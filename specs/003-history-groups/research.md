# Research: History Groups

Evidence gathered read-only on 2026-11-07 on macOS with Claude Code 2.1.319, Codex 0.167.0,
OpenCode 2.1.4 and pi 1.3.0. No harness state was modified. File contents were inspected for
structure (keys, names) only.

### OpenCode

Sessions live in `data/opencode/opencode.db` (tables `session`, `session_v2`, `message`, `part`,
`todo`). The same database contains `account` and `control_account` (with `access_token`,
`refresh_token`), `credential` (`value`) and `session_share` (`secret`). Sessions cannot be
separated from credentials. `storage/` is the pre-database store and no longer written.
**Decision**: the OpenCode definition declares no history entries; OpenCode does not support
groups in this feature (FR-003). `group create opencode/...` fails with exit 2.

## R2. Account identifiers inside transcripts (FR-003)

Claude transcripts contain a `session-owner` record with `accountUuid` and `organizationUuid`;
Codex rollouts and threads carry account ids. These are identifiers, not secrets or login data.
**Decision**: FR-003's ban covers entries that hold credentials or login data (tokens, secrets,
login records); account identifiers embedded in conversation records do not make an entry
ineligible. `show` and `help sharing` say that shared conversations reveal which account wrote
them. The spec wording is aligned in FR-003.

## R3. Resuming another account's conversation (Claude Code)

The Claude binary contains "This session belongs to another account, so nothing was sent". This
message most likely belongs to remote or bridged sessions, but it could also apply to resuming a
transcript whose `session-owner` differs. **Not verifiable without two real accounts.** The
feature does not depend on it for correctness (files are shared either way), but SC-001 is about
reachability, and US1's resume under another account is a manual walkthrough check
(quickstart step 6). If Claude refuses, the limitation is documented and the use case narrows to
profiles of the same account with different endpoints or models.

## R4. Symlinks versus a native session directory variable

pi already supports `PI_CODING_AGENT_SESSION_DIR`, which could point straight at a group store.
**Decision**: use links for all harnesses. One mechanism keeps the planner, `show`, `doctor` and
drift handling data-driven (Constitution I), and the existing pi pin of the session directory
under the profile stays unchanged.

## R5. Where groups and stores live

**Decision**:
- Group records: `<config>/aprofile/groups/<harness>/<group>.yaml` (config, like profiles and hook
  sets; holds the name and creation time). `home` has no record; it is synthesized for every
  harness whose definition declares history entries.
- Group stores: `<data>/aprofile/groups/<harness>/<group>/`, entries at the same relative paths as
  in a config dir.
- Set-aside history: `<data>/aprofile/set-aside/<harness>/<name>/<timestamp>/` with a
  `manifest.json` listing each item's original relative path and the reason (collision, not
  mergeable).
Alternatives rejected: keeping groups inside `settings.yaml` (one file for unrelated concerns, and
deleting a group would rewrite global settings); putting set-aside history in the profile config
dir (reported as unclassified, possibly scanned by the harness; clarified in the spec).

## R6. Moving files across file systems

Join moves files from a profile config dir (`<data>/aprofile/profiles/...`) into a store under
`<data>` or the default location under `$HOME`. These are normally on one file system.
**Decision**: `os.Link(src, dst)`, which fails with `EEXIST` and never overwrites, then remove
the source; on `EXDEV`, copy to an `O_EXCL` target (preserving mode and modification time), fsync,
then remove the source. `os.Rename` is not used because it silently replaces an existing file.

## R7. Leak detection must learn about groups

Today `layer.planRule`/`leakingLink`, `layer.treatmentFor` and `doctor.isolationFindings` treat
every linked state entry as a leak, and `sync --fix-links` would replace a member's history link.
**Decision**: the planner and treatments receive the profile's expected history store (empty for
isolated profiles). A history link whose target is the expected store path is correct; any other
link on a state entry keeps the current leak handling for isolated profiles, and for members a
history link to the wrong target becomes a `fix-link`-style relink (FR-022c).

## R8. Override and classify paths must keep the history fields

`mergeRulesByEntry` replaces a whole rule when a `harnesses.d` override names the same entry, and
`harness classify` writes `{entry, layer}` only; `expandCompanions` builds companion rules without
extra fields. **Decision**: companions copy `history` and `merge`; `harness classify` keeps an
existing rule's history fields when the new category is `state` and drops them otherwise (with a
note); overrides replace rules as today, and the contract documents that an override of a history
entry must restate `history`.

## R9. Running check

`profile.RunningProcess(configDir)` is reused for membership changes (exit 4). `remove --purge`
has no running check today and does not need one for this feature: `os.RemoveAll` removes a
symlink itself and never follows it (verified in the Go standard library), so group stores are
safe (FR-019); a test pins this.
